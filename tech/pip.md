# pip, virtual environments and lock files

## What it is

pip is the program that installs Python packages from the Python Package Index (PyPI), a public store of libraries. A **virtual environment** (venv) is a private folder holding its own Python and its own installed packages, so one project's libraries do not mix with another's. A **requirements file** lists what to install. A **lock file** is a requirements file that pins *every* package, including the ones your packages need, to exact versions, and here also to exact file hashes. pip comes with Python (the `setup-python` action and Python 3.13 both provide a recent one).

## Why this repository uses it

The CI cache is keyed on the hash of the lock file, so there must be one file whose contents change exactly when a dependency changes. The same file must work on six combinations (Linux and Windows, Python 3.10 to 3.12). Hashes mean pip refuses a package file that is not byte-for-byte the one that was locked, which protects against a compromised or replaced upload.

## How it works underneath

`python -m venv .venv` copies (or links) a Python interpreter into `.venv/bin/` and makes an empty `site-packages` folder. Running `.venv/bin/pip install X` downloads X from PyPI and unpacks it into that folder. When you run `.venv/bin/python`, `import X` finds it there. Nothing outside the folder changes. pip caches the files it downloads in a **cache directory** (`python -m pip cache dir` prints where), and `setup-python`'s `cache: pip` saves and restores that folder between CI runs.

A **hash** is a fingerprint computed from a file's bytes. If one byte differs, the fingerprint differs.

## Walkthrough of this repository's use

### The input files

```text
numpy==2.1.3
pandas==2.2.3
pytest==9.0.3
```

`==` pins one exact version. These are the packages the project names itself.

### The lock file

```text
colorama==0.4.6 ; sys_platform == 'win32' \
    --hash=sha256:08695f5c... \
    --hash=sha256:4f1d9991... \
    # via pytest
coverage==7.16.2 ; python_full_version < '3.11' \
```

Each entry is a package at an exact version. After `;` is an **environment marker**: a condition. `colorama` is installed only on Windows (`sys_platform == 'win32'`), and this `coverage` only on Python older than 3.11 (a different `coverage` entry covers newer Pythons). Each `--hash=sha256:...` is an allowed file for that package (there is one per platform build); the trailing `\` continues the line. `# via pytest` records why the package is there. Because the markers are in the file, one lock works for every cell of the matrix.

### Installing

```bash
.venv/bin/pip install -q --require-hashes -r requirements-dev.txt
.venv/bin/pip install -q --no-deps -e .
```

`-q` is quiet. `--require-hashes` makes pip refuse any package that has no hash or whose download does not match. `-r FILE` reads requirements from a file. The second command installs the project itself: `-e .` means **editable** (the installed package points at your source folder, so edits take effect without reinstalling), and `--no-deps` stops pip from resolving dependencies again because the lock already installed them.

### In the workflow

```yaml
- uses: actions/setup-python@...
  with:
    python-version: ${{ matrix.python }}
    cache: pip
    cache-dependency-path: requirements.txt
- run: pip install --require-hashes -r requirements.txt
```

`setup-python` builds a cache key from the operating system, the Python version and the hash of `requirements.txt`, restores pip's download cache before the install and saves it after. `pipeline/cache_key.py` is a small model of that key. Changing one pinned version changes the file hash and so the key, which is how a stale cache is never reused.

## Try it yourself

1. `.venv/bin/pip --version` shows the pip and Python in the venv.
2. `.venv/bin/pip list | head` lists installed packages with versions.
3. `.venv/bin/pip cache dir` prints the cache folder.
4. `.venv/bin/python -m pipeline.cache_key` prints `setup-python-Linux-x64-python-3.12.7-pip-<64 hex characters>`; edit one pin in a copy of the file with `--file` and the hash changes.
5. `grep -c "^[a-z]" requirements.txt` counts the locked packages.

## Mistakes people make

- Running `pip install` without a venv and changing the system Python.
- Forgetting to activate or to call `.venv/bin/pip`, then installing into the wrong place.
- Hand-editing a lock file; regenerate it (see `uv.md`).
- Using `--require-hashes` with a file that has an unhashed line: pip stops with an error.
- Assuming a lock made on macOS works on Windows; a non-universal lock misses `colorama` and the like. This one is universal.

## Check yourself

1. What does a virtual environment isolate? *(The installed packages and the interpreter copy, per project.)*
2. What does `--require-hashes` guarantee? *(Every installed file matches a hash in the file.)*
3. What does `; sys_platform == 'win32'` mean? *(The package is installed only on Windows.)*
4. What does `-e .` do? *(Installs the project in editable mode, linked to the source folder.)*
5. Why does changing `requirements.txt` cause a cache miss? *(The cache key contains the file's hash.)*
